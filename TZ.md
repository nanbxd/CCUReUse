# Техническое Задание (ТЗ): Модуль студенческих мероприятий (Caspian Events)
**Статус:** Черновик для команды разработки (codex)  
**Контекст:** Интеграция в существующий сайт шеринга колледжа (общая база пользователей)  
**Тип архитектуры:** Модульная / Микросервисная (новые таблицы для ивентов)

---

## 1. Общее описание функционала
Модуль предназначен для планирования, финансирования (краудфандинга) и контроля посещаемости студенческих мероприятий. Система решает проблему финансовой непрозрачности, плохой организации и ручного учета билетов.

---

## 2. Архитектура данных (Новые сущности в БД)

Необходимо добавить три новые таблицы в существующую базу данных, связав их с текущей таблицей пользователей (`Users`).

### Таблица `Events` (Мероприятия)
*   `id` (Primary Key, UUID)
*   `creator_id` (Foreign Key -> `Users.id`) — организатор
*   `title` (String) — название
*   `description` (Text) — описание, программа
*   `location` (String) — место проведения (ссылка на 2GIS / адрес)
*   `capacity` (Integer) — максимальная вместимость площадки
*   `target_budget` (Integer) — минимально необходимый бюджет для проведения
*   `ticket_price` (Integer) — цена одного билета
*   `min_tickets_required` (Integer) — сколько минимум билетов нужно продать (`target_budget / ticket_price`)
*   `status` (Enum) — текущий статус: `['exploration', 'crowdfunding', 'confirmed', 'cancelled', 'completed']`
*   `deadline_date` (DateTime) — дата окончания сбора средств
*   `event_date` (DateTime) — дата проведения мероприятия
*   `created_at` (DateTime)

### Таблица `Tickets` (Бронирования и билеты)
*   `id` (Primary Key, UUID)
*   `event_id` (Foreign Key -> `Events.id`)
*   `user_id` (Foreign Key -> `Users.id`) — студент-покупатель
*   `status` (Enum) — `['pending', 'paid', 'used', 'refunded']`
*   `kaspi_transaction_screenshot` (String, Nullable) — ссылка на сохраненный скриншот перевода
*   `qr_code_hash` (String, Unique) — уникальный хэш для генерации QR-кода (`sha256(event_id + user_id + secret)`)
*   `updated_at` (DateTime)

### Таблица `Reviews` (Отзывы)
*   `id` (Primary Key, UUID)
*   `event_id` (Foreign Key -> `Events.id`)
*   `user_id` (Foreign Key -> `Users.id`)
*   `rating` (Integer, 1-5) — оценка
*   `comment` (Text) — текст отзыва
*   `created_at` (DateTime)

## 3. Жизненный цикл мероприятия и логика бэкенда

Мероприятие должно строго проходить через следующие системные статусы:

1. **`exploration` (Разведка спроса):**
   * Отображается карточка с описанием идеи.
   * Кнопка для студентов: «Я бы пошел» (инкрементирует счетчик желающих). Деньги не собираются.
2. **`crowdfunding` (Сбор средств / Предзаказ):**
   * Активируется, когда организатор заполнил смету и указал реквизиты доверенного лица (кассира/старосты) для Kaspi-перевода.
   * Появляется прогресс-бар: `Продано Х из Y билетов для старта`.
   * Студент нажимает «Забронировать», видит реквизиты, делает перевод и прикрепляет скриншот. Билет создается со статусом `pending`.
   * Доверенное лицо (организатор) в своей панели проверяет Kaspi и нажимает «Подтвердить». Статус билета меняется на `paid`, генерируется `qr_code_hash`.
3. **`confirmed` (Успех) ИЛИ `cancelled` (Отмена):**
   * Наступает в момент `deadline_date`.
   * **Сценарий А (Успех):** Если `min_tickets_required` достигнут. Ивент переходит в `confirmed`. Билеты активируются.
   * **Сценарий Б (Отмена):** Если сумма не собрана. Статус меняется на `cancelled`. Всем покупателям высылается пуш/уведомление. Выводится список для организатора: кому вернуть деньги (с номерами телефонов из профилей). Статус билетов меняется на `refunded`.
4. **`completed` (Завершено):**
   * Наступает после даты `event_date`. Включается модуль отзывов.

## 4. Требования к UI/UX (Фронтенд-задачи)

Интерфейс должен быть адаптирован под мобильные устройства (Mobile-First Web).

*   **Экран «Афиша»:** Лента карточек. Публичные видны всем пользователям сайта, приватные доступны только по прямой UUID-ссылке (для групповых вписок). На карточке выводится шкала заполненности бара/площадки во избежание тесноты.
*   **Экран «Кабинет Организатора»:** 
    * Вкладка верификации платежей (список студентов в статусе `pending` с возможностью посмотреть скриншот чека и кнопкой `Подтвердить`).
    * Кнопка «Сканер входа» (запускает веб-камеру смартфона, считывает QR, отправляет POST-запрос на `/api/tickets/verify`).
*   **Экран «Билет Студента»:** Находится в личном кабинете существующего сайта. Рендерит QR-код на основе `qr_code_hash`. Показывает статус («Оплачен», «Использован»).
*   **Модуль Отзывов (Историческая память):** На странице архива ивентов первокурсники должны иметь возможность читать отзывы за прошлый год, отсортированные по организаторам или типам тусовок.

## 5. Безопасность и Модерация

1. **Ролевая модель:** Права на перевод ивента в статус `crowdfunding` и привязку Kaspi-карт имеют только пользователи с верифицированной ролью `Organizer` или `Admin` (выдается вручную ИТ-сообществом/студсоветом). Обычный студент может создавать только бесплатные приватные сходки (`exploration` / бесплатный `confirmed`).
2. **Анти-фрод на входе:** При успешном сканировании QR-кода сервером, статус билета БЕЗВОЗВРАТНО меняется на `used`. Повторный скан того же кода должен выдавать ошибку: *"Билет уже использован в [Время]"*.
